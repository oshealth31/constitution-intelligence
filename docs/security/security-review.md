# Security review (Stage 12)

A review of the code as it stood on 4 November 2026 (after Stage 11), what was changed, and
what is still open. **This review does not make the system "unhackable".** It lowers the
risk from the problems listed here. No tests were run against live systems: the system has not
been deployed, and every check ran against throwaway test databases with synthetic data.

How the review was done: every API route was listed with its access rule (see
`apps/api/src/modules/access/route-access.spec.ts`), and the guards, tenant isolation, file
storage, document parsing, AI integration, configuration, logging, audit log and web headers
were read line by line.

Severity: **High** = likely to cause serious harm if left; **Medium** = real harm under some
conditions; **Low** = limited harm or needs another failure first; **Info** = good practice.

## Problems found and fixed

| ID     | Area                                    | Severity | Evidence (before)                                                                                                                                                                                                                | Fix                                                                                                                                                                                                      |
| ------ | --------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S12-01 | API abuse, bots, denial of service      | Medium   | Only sign-in, password-reset requests and AI used a rate limit (`RateLimitService.hit` call sites). Search, offline download, reading and every other route could be called without limit.                                       | General limit per network address (`API_RATE_LIMIT_PER_MINUTE`, default 600/min) in `common/request-throttle.ts`. Health checks are not counted.                                                         |
| S12-02 | Brute force                             | Medium   | `AuthService.changePassword` checked the current password with no attempt limit: someone with a stolen session could guess it, then lock the owner out.                                                                          | 5 attempts per person per 15 minutes, then 429.                                                                                                                                                          |
| S12-03 | Brute force, bots                       | Low      | `POST /auth/password/reset` and `POST /invitations/accept` (public) had no attempt limit. The links are 256-bit random, so guessing is not practical, but scripts could hammer the routes.                                       | Per-address limit (same as sign-in: `LOGIN_MAX_ATTEMPTS_PER_IP` per window).                                                                                                                             |
| S12-04 | API abuse (email flooding)              | Medium   | `POST /organisations/:id/invitations` sends an email each time, with no limit: a compromised administrator account could send thousands.                                                                                         | 50 invitations per organisation per hour (`auth/abuse-limits.ts`).                                                                                                                                       |
| S12-05 | API abuse                               | Low      | Document uploads, logo uploads, answer/simple-word imports and payment reports had size and storage limits but no count limit.                                                                                                   | Per-organisation hourly limits (30 uploads, 20 logos, 30 imports, 20 payment reports). Upload limit is checked before the file is read.                                                                  |
| S12-06 | API abuse                               | Low      | `POST /ai/retrieval-preview` (a testing aid open to any member) searched without limit, bypassing the 120/hour "Find relevant clauses" limit. It only returns the member's own organisation's published text, so nothing leaked. | Shares the "Find relevant clauses" limit.                                                                                                                                                                |
| S12-07 | Cross-site scripting (defence in depth) | Medium   | The web app sent no Content Security Policy (`next.config.ts`: "A strict Content Security Policy is added in the security-hardening stage"). Any future XSS bug would run freely.                                                | Per-request nonce policy in `apps/web/src/proxy.ts`: only Next.js's own scripts run, no framing, no plugins, connections to this site only. A browser test checks injected scripts are blocked.          |
| S12-08 | Sensitive data exposure                 | Low      | API responses had no `Cache-Control`: browsers and proxies could keep members' data (for example on a shared computer).                                                                                                          | `Cache-Control: no-store` on every API response unless a route opts out (only the public logo does).                                                                                                     |
| S12-09 | Insecure configuration                  | Low      | API used Helmet defaults (a page-style policy, HSTS even locally, no resource policy).                                                                                                                                           | API policy `default-src 'none'; frame-ancestors 'none'`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, HSTS only once deployed. Web: HSTS (production), COOP.             |
| S12-10 | Authentication weakness                 | Medium   | Platform Super Admin sessions lasted like everyone else's (24 hours idle, 14 days absolute), although a Super Admin can affect every organisation.                                                                               | Super Admin sessions end after 30 minutes idle and 12 hours absolute (configurable). **Two-factor sign-in is still missing: see U1.**                                                                    |
| S12-11 | Session security                        | Low      | Session cookie name had no `__Host-` prefix, so a compromised sub-domain could plant a cookie.                                                                                                                                   | `__Host-ci_session` in staging and production (Secure, whole site, no sub-domains).                                                                                                                      |
| S12-12 | Sensitive data in logs                  | Low      | Failed sign-ins stored the typed email in the audit log even when no account existed. People sometimes type their password into the email box.                                                                                   | Unknown addresses and rate-limited attempts are stored masked (`s***@example.com`). Known accounts are recorded as before.                                                                               |
| S12-13 | Sensitive data in logs                  | Low      | Request and error logs included the full address, with query strings (search words: `?q=...`).                                                                                                                                   | Only the path is logged (`logging/path-only.ts`).                                                                                                                                                        |
| S12-14 | Malicious documents, denial of service  | Low      | PDF reading had a 500-page limit but no time or text limit: a crafted PDF could keep the server busy.                                                                                                                            | 60-second and 3-million-character limits, checked between pages. **A single pathological page can still block; see U4.**                                                                                 |
| S12-15 | Insecure configuration                  | Info     | Production accepted `LOG_LEVEL=debug` and a relative storage folder.                                                                                                                                                             | The API refuses to start in production with debug/trace logging; staging and production need an absolute storage path.                                                                                   |
| S12-16 | Dependency vulnerabilities, secrets     | Info     | CI audited high/critical production dependencies; Dependabot existed. No secret scanning.                                                                                                                                        | New "Security scans" workflow: full dependency report, failing audit for high/critical, and a gitleaks scan of the whole git history, on every pull request and weekly. Dependabot groups minor updates. |

## Reviewed, no problem found

Each line says what protects it and where it is tested.

| Area                                      | What protects it                                                                                                                                                                                                                                                                                | Tests                                                       |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Broken access control                     | Every route needs a session unless marked `@Public()`. Organisation routes check membership and role in the database on every request (404 for non-members, 403 for wrong role). New: a test fails if any route lacks an access rule.                                                           | `route-access.spec.ts`, `access.e2e.spec.ts`                |
| Cross-tenant data leakage                 | Database row-level security (role `app_tenant`) plus an explicit organisation filter in every query; files stored under `tenants/<id>/` and checked on every read.                                                                                                                              | `tenancy.e2e.spec.ts`                                       |
| Privilege escalation                      | Only Owners grant Owner; nobody grants above their own role or changes themselves; the Super Admin flag cannot be set through the API.                                                                                                                                                          | `access.e2e.spec.ts`                                        |
| SQL injection                             | All queries are parameterised (Drizzle `sql` templates). The one raw statement sets a fixed role name. Search patterns escape `%` and `_`.                                                                                                                                                      | Code review; malformed IDs are refused before queries.      |
| Cross-site scripting                      | React escapes all text; no `dangerouslySetInnerHTML` anywhere. Downloads are `attachment` with `nosniff` and a sandbox policy. Logos: PNG/JPEG/WebP only, checked by file signature (no SVG).                                                                                                   | `documents`, `portal` suites; new CSP browser test          |
| CSRF                                      | State-changing requests need the `X-Requested-With` header and an allowed `Origin`; the cookie is `SameSite=Lax`; CORS allows only listed origins.                                                                                                                                              | `security.e2e.spec.ts`                                      |
| SSRF                                      | The API never fetches an address supplied by a user. Its only outbound call is to the configured AI provider (switched off for launch).                                                                                                                                                         | Code review                                                 |
| Unsafe file uploads, path traversal       | 10 MB limit; PDF and DOCX only, checked by content; storage keys must match a strict pattern, stay in the organisation's folder and inside the storage root; files are never overwritten.                                                                                                       | `documents` suites, storage unit tests                      |
| Malicious documents                       | ZIP (DOCX) limits on entries and expanded size (zip bombs); PDF.js with scripts, fonts and forms disabled; password-protected files refused.                                                                                                                                                    | `documents-units.spec.ts`                                   |
| AI prompt injection and data exfiltration | Retrieval only ever sees the caller's organisation's published text. Every answer is checked on the server: citations must be exact quotes of passages given, no invented clause numbers, no leaked instructions. The AI key stays on the server. AI is off at launch (`AI_PROVIDER=disabled`). | `ai.e2e.spec.ts`, `ai-units.spec.ts`, `tenancy.e2e.spec.ts` |
| Unsafe retrieval and citations            | Citations link to sections of a published version of the same organisation only.                                                                                                                                                                                                                | `ai.e2e.spec.ts`                                            |
| Public file exposure                      | Only the organisation logo is public, taken from the branding record and restricted to the `branding/` folder. Constitution files need a signed-in member with the right permission.                                                                                                            | `portal.e2e.spec.ts`                                        |
| Subscription bypass                       | Checked by the server for every organisation route (state, features, limits), not by hiding buttons.                                                                                                                                                                                            | `subscriptions.e2e.spec.ts`                                 |
| Audit log tampering                       | Database triggers block UPDATE, DELETE and TRUNCATE on `audit_events`; the tenant role may only read and add its own organisation's events.                                                                                                                                                     | `tenancy.e2e.spec.ts`, `security.e2e.spec.ts`               |
| Secrets exposure                          | Settings validated at start-up (errors name settings, never values); no secrets in the repository (now scanned); logs never include headers, cookies, passwords or tokens.                                                                                                                      | `config.spec.ts`, secret scan                               |
| Credential stuffing                       | Per-email (5) and per-address (50) limits per 15 minutes; identical answers for wrong password and unknown email; Argon2id hashing.                                                                                                                                                             | `auth.e2e.spec.ts`                                          |

## Unresolved risks

These need a decision, money or the deployment stage. They are listed so nobody mistakes the
system for finished.

| ID  | Risk                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Severity             | What would resolve it                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| U1  | **No two-factor sign-in.** A stolen Super Admin or Owner password is enough to get in.                                                                                                                                                                                                                                                                                                                                                                  | High (before launch) | Authenticator-app (TOTP) codes with recovery codes, required for Super Admins and offered to Owners/Administrators. A separate piece of work.       |
| U2  | **Not deployed; production protections do not exist yet.** HTTPS certificates, firewall/DDoS protection, monitoring and alerting, and in-country hosting (Botswana DPA) are all still to be set up.                                                                                                                                                                                                                                                     | High (before launch) | Deployment stage, with your approval.                                                                                                               |
| U3  | **The API connects to the database as its owner.** Row-level security applies to organisation work (the API switches to `app_tenant`), but platform queries run with full rights, and the owner could switch off the audit-log triggers.                                                                                                                                                                                                                | Medium               | In deployment: a separate migration account that owns the tables, and a runtime account that does not (and cannot disable triggers).                |
| U4  | **Documents are parsed inside the API process.** The new time limit is checked between pages; one crafted page could still block the server, and there is no antivirus scan.                                                                                                                                                                                                                                                                            | Medium               | Parse uploads in a separate worker process with hard time and memory limits; optionally scan with an antivirus engine.                              |
| U5  | **Rate limits depend on correct proxy settings.** In production the browser talks to the web app, which forwards to the API, so there is at least one proxy hop. Unless `TRUST_PROXY` matches the real setup, every user appears to share one address: the sign-in limit (50 per address) would then block everyone. The general limit is counted per copy of the API, so it is weaker across many copies and does not stop a large distributed attack. | Medium               | Set `TRUST_PROXY` to the real number of trusted hops at deployment and test it; add protection in front of the API (hosting firewall/CDN).          |
| U6  | **Account lock-out and weak-password gaps.** Anyone who knows an email address can trigger the 15-minute sign-in lock for it. No check against known breached passwords.                                                                                                                                                                                                                                                                                | Medium               | Breached-password check (offline list or k-anonymity service, subject to data-protection review); consider step-up checks instead of hard lock-out. |
| U7  | **No backups yet**, so backup access cannot be reviewed.                                                                                                                                                                                                                                                                                                                                                                                                | Medium               | Encrypted, in-country backups; access limited to named staff; restores tested regularly; retention matching docs/subscriptions.md.                  |
| U8  | Audit log is append-only inside the database but not tamper-evident (no signature chain) and not copied elsewhere.                                                                                                                                                                                                                                                                                                                                      | Low                  | Ship audit events to separate write-once storage, or add a hash chain.                                                                              |
| U9  | Web pages allow inline styles (`style-src 'unsafe-inline'`), used for brand colours. Styles cannot run code; an injected style could change how a page looks.                                                                                                                                                                                                                                                                                           | Low                  | Move brand colours to CSS classes/variables set without inline attributes.                                                                          |
| U10 | Copies saved for offline reading stay on a device until it next connects or the person signs out (see docs/offline.md).                                                                                                                                                                                                                                                                                                                                 | Low                  | Accepted by design; members are told not to save on shared computers.                                                                               |
| U11 | No independent penetration test. GitHub's code scanning (CodeQL) is not available for this private repository without a paid plan.                                                                                                                                                                                                                                                                                                                      | Low                  | An external test before launch; enable code scanning if the plan changes.                                                                           |
| U12 | The new secret scan and full dependency report run in CI; their first results are recorded in the Stage 12 pull request, not here.                                                                                                                                                                                                                                                                                                                      | Info                 | Review the reports; Dependabot pull requests need someone to merge them.                                                                            |

The pre-launch list is in [checklist.md](checklist.md).
